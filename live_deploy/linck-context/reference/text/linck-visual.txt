LINCK IN MOTION (linck-visual.html): what each animation shows

Sixteen scenes on a 1600×900 SVG stage, each 12–22 s. Numbers marked
"measured" come from tests/bench; the others are design or estimates.

1. Linck in one picture. Phone, laptop and your code reach an edge, then
   the live gateway, product API and control. A cell holds the supervisor
   (Python, Go, Rust, TypeScript), market data, tick cache, orders & risk
   (the only writer of money) and a broker gateway; the exchange and brokers
   sit outside; the ledger and journal sit below. Animated: ticks flow in, an
   order goes out, a fill comes back, +₹1,240 reaches the phone, "deploy v7"
   reaches the supervisor.

2. Why it is split up. Today: one Python process (website, Kite feed, money,
   8 strategies); a deploy restarts everything. First build: Core API,
   runner workers, market data, orders & risk; a deploy restarts only the
   Core API while the runners keep trading. Final: a platform band over 10
   cells; one cell goes bad, the rest carry on.

3. A price, from exchange to strategy. Exchange → feed handler → sequencer
   → tick cache (one slot per instrument) → supervisor → strategy, with the
   hop labels (WebSocket, in process, gRPC latest, shared memory, socket
   ~50 µs). While the strategy is busy, new prices overwrite the slot; the
   next batch says "skipped 2".

4. A slow strategy: queue vs latest. Top: a queue fills up and the strategy
   decides on older and older prices. Bottom: one slot, always the newest.
   Test-run results: 3.5 s old through a queue vs 44 ms through latest-only
   (measured, tests/bench/runtime/promises.py).

5. Your code becomes something we can run. strategy.py, main.go, lib.rs and
   index.ts go through a builder with a pinned image per language (uv, go
   build, cargo, npm) into a package layer, static binary, native binary and
   JS bundle; certification (fault matrix, same twice, budgets); a signed
   registry.

6. Every language, one runtime host. A tick cache in shared memory and one
   supervisor for all languages. A Python parent with the SDK loaded once
   forks each strategy (~2 MB each, measured); main.go and lib.rs become
   binaries run as processes (4 MB, 2 MB); index.ts becomes a bundle run by
   Node (42 MB). Each runs in a sandbox and talks to the supervisor over a
   Unix socket: Hello, Ready, then Batch/Done in a loop. WASM runs inside
   the supervisor; a strategy on your own machine gets the same messages
   over a gRPC stream. Round trip ≈ 40–60 µs in every language (measured).

7. One batch, message by message. Lifelines for journal, supervisor and
   strategy: Batch 812 (kept in the journal first), Request option chain,
   Reply from host cache, Done sell CE + PE (sent on to orders & risk),
   Batch 813 with the fill, Done nothing to do, Snapshot?, state at 813.

8. An order, from decision to fill. Strategy (epoch 4) → intent log written
   first (ids dep7:812:0, dep7:812:1) → orders & risk gates (epoch current?
   id new? risk ok?) → ledger (order + outbox in one transaction) → broker
   gateway → Kite. A shadow copy goes to the sim venue: "would fill ₹22
   worse". The fill comes back; P&L goes to the phone; batch 813 to the
   strategy.

9. A crash costs milliseconds. Process A (epoch 1) runs to batch 458 and
   crashes; B (epoch 2) restores the snapshot at 400 and catches up 57
   batches; an order made again is refused as already placed. 14 ms (Go),
   38 ms (Python), orders identical (measured).

10. The same bug twice: stop, don't loop. Two tries crash on batch 250 with
    the same error → quarantined: no new entries, no restart loop;
    square-off, stops and kill switch still work. `linck replay --from 200
    --to 250` reproduces it on a laptop.

11. Two copies, only one may trade. A zombie A (epoch 1, feed 3 min late)
    and the real B (epoch 2). With epochs: A placed 0 of 134, B 133 of 133.
    With ids only: A placed 134 of 134 at wrong prices, B 5 of 133 (measured).

12. Replay any day, repair a bad one. The live run and its journal; a replay
    from the snapshot at 300 matches all 300 batches; an ambiguous candle at
    311 branches into "up first" and "down first"; the owner picks one,
    presses Push (checked again, then applied), and can undo.

13. Would Kite really have taken it? A paper fill SELL 75 walks the bids
    (25 @ 120.40, 30 @ 120.20, 20 @ 120.00; average 120.21) above a 119.90
    limit; six checks pass; "would fill ₹22 worse". A SELL 70 fails lot
    size ("would be rejected"). The ready-for-live card: 20 sessions,
    nothing refused (fails here), within 1%, no repair open.

14. Any broker, whatever its SDK language. A broker gateway pod: a Go core
    (never twice, rate limits, order state, reconcile); Kite, Angel One and
    Upstox adapters in process in Go; Dhan in a Python sidecar using its
    official SDK over gRPC on a Unix socket. The sidecar dies: Dhan pauses
    new entries, the others carry on; it restarts and reconciles.

15. Room for thousands. One host (16 vCPU, 64 GB, keep 40% free) ≈ 3,500
    strategies, ≈ 14 GB; a cell of 3 hosts ≈ 10,000; 2 cells ≈ 20,000; more
    cells added when needed. Estimates from 07-brokers-latency-load.md
    (20,000 strategies ≈ 4–6 hosts in 2 cells).

16. From a laptop to live money. Write (laptop) → run a past day (seconds)
    → backtest (minutes) → certify (faults, same twice, budgets) → paper
    (days) → shadow (weeks) → live with 1 lot → watched every day (day
    check, issues, repair).
