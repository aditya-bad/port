 How Linck keeps its promises

 The platform explained from what it promises a user, not from its boxes. For each promise: the mechanism in plain words, a worked example, and the evidence, marked by whether it runs in your app today, works in a prototype, was measured, or is still a design.

 00The short answer
How the platform keeps its promises, and how sure we are of each.

No single part is trusted to be perfect. Five plain mechanisms, each doing one job, carry every promise.

The runtime owns time, inputs and state · prices keep only the latest value, while orders and fills are a log · one service writes money, and checks an id and an epoch on every order · every input is numbered and kept, so any moment can be replayed · every paper fill is checked against what the market would really have given.

Earlier documents described the parts. This one starts from what Linck promises a user and shows, promise by promise, how it is kept, with a worked example and the evidence. Each piece of evidence is marked:

 02Promise 1 · Every decision is on the latest price
You asked: a client stuck while 3 ticks arrive must get the latest one next. Here is that, measured.

How

One slot per instrument for each receiver. A new price overwrites the old one. Nothing ever queues behind a busy strategy.

One batch in flight. A busy receiver isn’t sent anything. When it’s ready it gets the slots that changed, which are the newest values, and how many it skipped.

Numbered prices. Each instrument’s updates carry a sequence number, so an older price can never overtake a newer one, even after a reconnect.

A reconnect starts from a snapshot of the latest values, never a backlog.

Fills, order updates and timers are the opposite: a separate lane, every one delivered, in order.

Why no transport does this for you

gRPC, WebSocket and SSE all run on TCP, which never drops: old ticks wait in buffers and are read first.

NATS can drop the newest message or disconnect a slow client.

Kafka-style logs replay a backlog by design.

So the guarantee is our own few lines of code at every hop. With them, the transport underneath matters little, and we use the simplest: gRPC streams between services, shared memory on a host, a socket into the strategy.

Measured: a strategy that takes 40 ms to decide, fed a tick every 5 ms prototype measured

With conflation, every decision is on a price about 43 ms old, which is the strategy's own decision time, and 500 ticks were skipped and counted.]

Same result in Go and Python (tests/bench/runtime/promises.py). Conflation made fewer decisions because there was nothing new to decide on once the feed stopped; the queue was still working through prices up to 3.5 seconds old. “Latest” isn’t “fresh”: if the feed itself stops, the latest price is old, and stall detection says so (your app already does this since 21 Oct).

Your app today: each runner and each open screen has a queue of up to 1,000 tick batches, dropping the oldest only when full, and ticks up to 5 minutes old are still processed. At today’s size strategies are fast enough that this rarely shows, but it is the queue line above. Step P0 replaces it with conflation in the current Python, in days.

 03Promises 2 and 3 · Each order once, from the right process
What stops a lost order, a doubled order, and two copies of a strategy trading at once.

Never lost

The strategy’s intent is written to a durable log before anything is sent.

The order service writes the order and an “outbox” row in one database transaction; a relay publishes the outbox. Nothing is saved without being announced, or announced without being saved.

Our order id travels in the broker’s tag field. After a reconnect we ask the broker for every tagged order of the day before sending anything new.

Never doubled

The id is deployment:batch:position, made by the SDK, never by the user. Replaying batch 458 makes exactly the same ids again.

The order service refuses an id it has already seen. A retry, a replay or a catch-up after a crash can’t place a second order.

Never two copies

A deployment runs under a lease. When the lease moves (a crash, a dead host, a network split), the new process gets the next epoch.

Every intent carries its epoch. The order service refuses anything older than the current one, before it looks at anything else.

Why the id alone isn’t enough: a process the supervisor gave up on may still be alive (a “zombie”). It is usually ahead of its replacement, which is still starting. Its orders arrive first, use the same ids, and win.

Measured: a zombie on a feed 3 minutes late, and its replacement prototype

[Diagram: A zombie process and its replacement. Process A runs with epoch 1 until batch 300, when it loses its lease but keeps running on a late feed. Process B starts from snapshot 300 with epoch 2. The order service refuses every order carrying epoch 1 and places B's.]

Order service | Zombie’s orders (stale prices) | Replacement’s orders (real prices) | 
With the epoch check | 134 sent · 0 placed · 134 refused as an old epoch | 133 sent · 133 placed | 
Ids only, no epoch check | 134 sent · 134 placed | 133 sent · 5 placed · 128 refused as “already placed” | 

Go and Python alike. Without epochs, the wrong process trades and the right one is blocked by its own ids, which is the failure fencing exists for. The earlier prototype also showed the crash case: killed at batch 458, restored from 400, 57 batches caught up in 14 ms (Go) / 38 ms (Python), the one re-made order refused, orders identical to a run with no crash.

Your app today: one process, and every fill goes through one database transaction (record_fill), so there is no second copy and no network between decision and booking. Ids, epochs and the outbox arrive with the separate order service (steps I1–I3); deterministic ids and epochs are worth adding to today’s runner first, because they make repair safer too.

 05Promise 5 · Any day can be replayed, and repaired
The same mechanism behind the day check, repair, replay and backtests.

Today, in your app running today

The day check and repair rebuild the day from Kite’s 1-minute candles, each minute played as four ticks.

Where a minute could have gone either way, both ways are played and you choose.

A plan is applied only if it comes out exactly as you reviewed it, with an undo.

Limits: a candle isn’t the ticks the strategy really saw, and it only works for Python strategies, because it copies the strategy object in memory.

The design prototype

Every batch the strategy was given is in the journal, by number. A replay starts a fresh process of the same version from the snapshot just before, and feeds those batches.

It reproduces live exactly, skipped ticks included; every state hash is checked. The first batch whose decision differs is the answer to “what went wrong”.

An ambiguous stretch: two processes from the same snapshot, one per reading. No copying, so any language works.

Prototype: a walk from snapshot 300 matched live on every one of 300 batches; reading 4 batches the other way parted at batch 311; Go and Python made the same decisions on all 600.

Candles are still needed for a stretch the app never saw (a stall), as today. The journal costs ~60–120 bytes a batch because it references prices in the tick archive instead of copying them (estimate: ~8 GB compressed a day for 2,000 strategies).

 07Promises 7 and 8 · Any language, and isolation
Why the runner’s own language never matters, and what keeps one strategy from hurting another.

Any language

The runner never imports, links or interprets your code. It starts a process and exchanges numbered messages with it: Hello, Ready, Batch, Request/Reply, Done, Snapshot.

Each language needs only a thin SDK that speaks those messages, a build image and a pass of the conformance suite.

Measured round trip, runner to strategy and back: about 40–60 µs in Rust, Go, Node and Python alike measured. Python is forked from a preloaded parent: about 2 MB of its own instead of 52 MB measured.

So moving the runner from Python to Rust later changes nothing for any strategy.

Isolation

A strategy is its own process: its crash, leak or infinite loop is its own prototype.

Budgets per batch and per minute; past them it is rested and restarted.

No network, files or broker tokens inside a strategy; it can only ask the supervisor.

In the cloud, a gVisor sandbox around each process; its cost per round trip isn’t measured yet design only.

Your app today: all strategies share one Python process. Errors are caught and a failing strategy is rested, but a strategy that blocks the event loop would slow everyone. That changes at step I2.

Memory and the opening burst set the size, not CPU per decision. The biggest real delay today isn’t compute at all: it is Kite calls inside decisions (2–11 per entry, ≥0.35 s apart). Answering those from local caches is what makes decisions fast.
