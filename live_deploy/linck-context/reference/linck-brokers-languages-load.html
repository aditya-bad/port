Brokers, languages and load

Three gaps in the architecture, answered with designs and measured numbers: brokers whose SDK isn’t in Go, how one runner runs strategies in any language while it moves from Python to Rust, and how fast the tick path is and how much it carries.

00

The three answers

Your three concerns, answered in a line each; the sections after show the design, the costs and the numbers.

Brokers without a Go SDK

We don’t need a broker’s SDK to be in Go. We need its API.

An adapter only translates. It runs in process when it’s Go, or as a sidecar in the broker’s own SDK language, behind one gRPC contract. The core that handles money is written once.
Many languages, one runner

The runner never runs strategy code. It runs processes that speak one protocol.

Each SDK speaks the protocol; the runner only starts, feeds and restarts processes. That’s why Python → Rust for the runner changes nothing for any strategy.
Latency and load

Our own code is microseconds. Today’s real delay is seconds, and it comes from Kite calls in the decision path.

Measured: a strategy decision is 7–47 µs; a cross-language round trip 39–200 µs. A trade waits on 2–11 Kite calls spaced ≥ 0.35 s apart. Removing those is the big win.

Every figure is marked measured (with the program that measured it, in tests/bench) or estimate (not measured yet, with how we’ll measure it). Measured on 23 Oct 2026 on a 4 vCPU Xeon 2.8 GHz cloud VM with 16 GB; it runs inside a sandboxed container, where a context switch costs more than on bare metal, so the round-trip figures are on the slow side.

01

Brokers whose SDK isn’t in Go

Dhan’s official client is Python; Upstox has no Go SDK; Fyers recommends Python or Node for its sockets. The gateway is Go. Here’s how both are true.

A broker SDK is a convenience wrapper. Underneath, every broker here is HTTPS for orders and a WebSocket for prices and order updates. The money-critical work isn’t in the SDK at all, and we write it once, in the gateway core. That work is the idempotency tag, rate limits, the order state machine, reconnect and reconciliation. An adapter only translates our order into the broker’s request and its replies back. So the question isn’t “is there a Go SDK”, it’s “where does the translation run”.

The contract every adapter implements

service BrokerAdapter {            // linck.broker.v1 — the same for Go adapters and sidecars
  rpc Capabilities(Empty)        returns (Caps);          // basket margin? modify? tag length? max legs?
  rpc Login(LoginRequest)        returns (Session);       // the broker’s daily login / token refresh
  rpc Place(PlaceRequest)        returns (PlaceResult);   // our order id goes in the broker’s tag
  rpc Modify(ModifyRequest)      returns (PlaceResult);
  rpc Cancel(CancelRequest)      returns (PlaceResult);
  rpc OrdersByTag(Day)           returns (OrderList);     // reconcile after a reconnect: find, never place twice
  rpc Positions(Account)         returns (PositionList);
  rpc BasketMargin(Basket)       returns (Margin);
  rpc OrderUpdates(Account)      returns (stream OrderUpdate);   // the broker’s socket or postbacks, in order
  rpc Ticks(Subscription)        returns (stream TickBatch);     // only where the user’s own broker feed is used
}

What a sidecar never does

  • Decide whether to retry, or how many times. The core does, with the tag, so a retry finds the first attempt.
  • Hold limits or counters. A token bucket per key and account lives in the core.
  • Talk to anything but its broker and the core: no database, no bus.

When a sidecar dies

  • The core marks the broker down, stops new entries, queues exits and alerts, as for a broker outage.
  • Kubernetes restarts the container in seconds; the core calls OrdersByTag and reconciles before sending anything new.
  • The sidecar’s SDK version is pinned in its image; upgrades go through the same conformance suite as a Go adapter.

Tested the same way, whatever the language

One conformance suite runs against the gRPC contract, not the code: recorded order conversations (accepted, rejected, partly filled, cancelled), reconnects mid-order, duplicate submits, rate-limit replies. Go adapters and sidecars pass the same suite before they see a paper order. Then come a paper week with shadow orders and a smoke test every morning before 09:00.

Prices from a Python-only socket

The same pattern on the market-data side: a feed sidecar decodes the broker’s socket with its SDK and streams our 32-byte record to the feed handler over the same kind of Unix socket. Python decodes a record in about 1 µs measured, so one core decodes on the order of a million updates a second. One broker connection carries a few thousand instruments (Kite allows 3,000 a connection and 3 connections a key, per its forum, kite.trade). Python is not the bottleneck there.

02

Many languages on a runner written in one

If strategies come in Python, Go, Rust and TypeScript, how does a Python runner, and later a Rust one, run them all?

The runner is a process manager and a message router. It never imports, links or interprets strategy code.

A strategy is a process that speaks the runtime protocol. Its language only matters inside its own process.

The runtime protocol, v1

Length-prefixed protobuf frames on a Unix socket the supervisor opens for each strategy. Generated types in every SDK from one set of .proto files, so no SDK can drift.

DirectionMessageWhat it carries
supervisor → strategyHelloprotocol version, deployment, parameters, the last saved state, its instruments
strategy → supervisorReadySDK name and version, what it subscribes to (instruments, bars, computed streams, timers)
supervisor → strategyBatchsequence number, now, the latest value of each changed instrument, bars, fills, order updates, timers
strategy → supervisorRequestchain, quote, history, instrument lookup: answered from the host’s caches, never the network
supervisor → strategyReplythe answer, within the same batch
strategy → supervisorDonethe batch’s sequence, commands (orders, baskets, cancels, timers), decisions for the log, a state delta
bothSnapshot · Stop · Log · Heartbeatstate saved with its sequence; a clean stop; logs; liveness

The rules that make it work in any language

  • One batch in flight. A slow strategy gets the latest values when it’s ready, never a backlog (the latest-value rule from the architecture doc).
  • Fills, order updates and timers are never conflated, and arrive in order.
  • No network inside a strategy. Everything it may ask for, it asks the supervisor, which answers from local caches.
  • One clock: now in the batch. That makes a strategy replay identically in a backtest, on a laptop and in the cloud.
  • Budgets: a strategy that doesn’t answer within its budget (50 ms by default) is marked slow; past 1 s it’s restarted from its last state.

What lives where

  • Once per language, in the SDK: the API (on_tick, ctx, params, state), the event loop that speaks the protocol, state save and load, a test harness.
  • Once for every language, in the platform: the supervisor, scheduling, leases, the tick cache, orders and risk, the broker gateway, logs, the backtest engine.
  • A new language is a new SDK, a build image and a pass of the conformance suite: recorded days with the expected decisions. Nothing in the platform changes.

At a few ticks a batch the round trip is the same everywhere, ~40–60 µs, because the cost is the operating system passing the message, not the language. Only with hundreds of ticks a batch does Python’s per-record decoding show, at about 1 µs a tick. For scale, today’s own Python strategy code takes 7–11 µs per tick at p50 measured, and today’s runner spends 60–150 µs around it measured.

Memory decides how Python strategies are started

A Python process that imports today’s strategy code is 52 MB measured. One process per strategy, started from scratch, would be ~100 GB for 2,000 strategies. So Python strategies are forked from a preloaded parent (a “zygote”): the SDK and libraries load once, every strategy is a fork, and they share those pages. Measured with 20 forked strategies, each holds ~2 MB of its own (3.6–4.5 MB counting its share of the parent) measured. Go and Rust need no trick (2–4 MB). Node is 42 MB a process, so TypeScript strategies are counted against a tenant’s budget until a WASM build of the TypeScript SDK replaces Node for dense hosting estimate.

From today’s Python runner to Rust, without touching a strategy

  1. Protocol v1 and the Python SDK. Today’s StrategyBase keeps working through a shim. runner.buy() becomes a command, resolver.get_leg_by_premium() a request answered from the cache. The existing Python runner gains a “process mode”: it forks each strategy from the zygote and talks protocol to it. Both modes run side by side in paper, and the decision logs must match for a week.runner: Python
  2. Go, Rust and TypeScript SDKs. They run against the same Python runner. That proves the runner is language-free before any Rust exists.runner: Python
  3. The Rust supervisor replaces the Python runner behind the same protocol, deployment by deployment, by lease handoff at a minute boundary outside 09:10–09:20 and 15:10–15:25.runner: Rust
  4. Dense hosting. WASM components for Rust, Go and TypeScript strategies on plans that need thousands a host. Python stays a forked process until Python-on-WASM is fast enough.later

Considered, and why not

OptionWhy not as the default
Embed Python in the Rust supervisor (PyO3)Saves the ~60 µs round trip, but one strategy’s crash, leak or blocking call takes the supervisor and every other strategy on the host down with it.
One process per language running many strategiesFewer processes, but strategies share a heap, a GIL and a crash; isolation and per-strategy budgets are what let us run other people’s code.
gRPC over TCP to each strategySame idea with more overhead; a Unix socket (or shared memory later) is enough on one host. TCP is kept for “bring your own process” users.
Every SDK rewritten as a thin client of a Rust core libraryKept for indicators (linck-core through PyO3, napi-rs and WASM), but the protocol, not a shared library, is what makes a language work.
03

Latency: where the time goes

From a price at the exchange to an order at the broker, hop by hop: what we measured, what we estimated, and what today’s app really does.

The finding that matters most

Our own code is microseconds. What makes a trade slow today is Kite REST calls inside the decision. Before its fills, an entry makes 2–11 of them measured: quotes to pick strikes by premium, an LTP to check, quotes for liquidity. The resolver spaces every Kite call at least 0.35 s apart, across the whole process, to stay under Kite’s rate limit. So one entry waits ~0.7–4 s plus Kite’s own response times. When several deployments enter at 09:20, they queue behind each other on that same throttle.

The fix is the design already in the architecture doc. The option chain and its prices are streams in the tick cache: subscribed when the strategy starts, kept fresh by the feed. A strategy’s “pick the strike nearest ₹100” becomes a Request answered from memory in microseconds. The decision path then has no network in it, and the only remote call left is the order itself.

The freshest a price can ever be is set by the feed, not by us. A broker’s socket sends snapshots, not every trade. How often per instrument is a number we’ll log from the live dispatcher before choosing a vendor feed.

What keeps it fast

  • Latest value only. Conflation means a busy moment costs one batch, not a queue, so latency doesn’t grow with load.
  • Route by instrument. Today every runner looks at every tick, so the cost is deployments × ticks. The new path indexes subscribers per instrument, so each tick touches only its subscribers.
  • Batching. At 16 ticks a batch the per-tick round-trip cost drops from ~50 µs to ~3–5 µs measured.
  • Binary records, fixed layout: decoding is under a microsecond in Rust and Go, ~1 µs in Python measured.
  • Shared memory between the feed and the supervisor on a host; a socket only to each strategy.
  • No network in a decision. Chains, quotes and history come from host caches.
  • No garbage collector on the hot path in the Rust parts; strategies pay only for their own.

The formula

ingest updates/s   = instruments × updates per instrument per second × open-burst factor
batches/s per host = strategies on the host × batches each per second
                     (≤ flush rate: 10 a second for tick strategies, ~1 a second for bar strategies watching their legs)
CPU per host       = batches/s × (round trip ~60 µs + the strategy’s own time)
memory per host    = strategies × (2–4 MB for Python, Go, Rust; 42 MB for Node) + caches
hosts              = max(CPU, memory) ÷ 60 %   // keep 40 % for the 09:15 open, a failed host, and moves

Strategy counts are deployments running at once. These sizes assume strategies as light as today’s (a decision in 7–47 µs). A heavy one, say a model scoring every tick, brings its own CPU, and the scheduler places it by its measured CPU history. The open-burst factor of 10× is an assumption until we log the real one.

Today’s ceiling, and the first fix

Today’s app is one Python process. Ticks go Kite → dispatcher → a broadcaster that hands every batch to every runner, and each runner filters for its own instruments. With 200 deployments that path tops out near 100 k ticks a second on one core before any strategy work measured, and a strategy that falls behind works through a queue of up to 1,000 old batches. Neither bites at today’s size: a few hundred instruments, well under 100 deployments. Both are fixed by step P0 in the architecture doc. P0 routes ticks per instrument and keeps a latest-value slot per runner instead of a queue. That’s a small change in today’s Python, and it removes the backlog risk now, long before Rust.

Correction to the architecture doc: its cell sizing assumed ~1 ms per strategy event (“3–5k strategies a host”). Measured, today’s strategies take 7–47 µs per tick and the runner ~0.1 ms around them, so host size is set by memory and the open burst, not per-event CPU.

Keeping the numbers honest

Estimates become measurements, and measurements become gates.

In the repository now

  • tests/bench/bench_runner.py: today’s runner per tick, a trade tick, Kite calls per trade, the broadcaster fan-out, forked-strategy memory.
  • tests/bench/ipc: the Rust supervisor, a strategy in each of Rust, Go, Node and Python, the fan-out and the conflation core. Standard libraries only.
  • Not in the deploy gate. They are run by name, and the results are pasted into this doc.

Next

  • Log the real feed: updates per instrument per second, the open burst, from today’s dispatcher. That turns the two biggest estimates into measurements.
  • Log every order’s broker round trip (sent → ack → fill) per broker, on the Repair page. That is the 20–200 ms estimate.
  • A replay load test: a recorded day at 1×, 10× and 50× through the whole path, with the tick-to-order p99 checked against the budget in section 03. It runs on every release from I2.
